Which embedding model

transcript-rag-agent runs sentence-transformers/all-MiniLM-L6-v2 on this machine: no key, no bill, already downloaded (about 90 MB), 384 dimensions. It reads only the first 256 tokens of what it embeds, and tau2 embeds each document whole. The 698 documents average about 330 tokens, and roughly 58% run past 256 (13% past 512), so for those it embeds the opening and drops the tail. The opening holds the title and key terms, so this may matter little. The replay below measures it rather than guessing: both MiniLM and Qwen3-Embedding-0.6B (32k context) are scored on the leaders' own dense queries against what OpenAI's model returned.

4 · Milestones 2–4 — native calls, banking's own optimiser, then the judge

Milestone 2 · native tool calls (T1, and P4 for free)

Today the sealed core gives the model no tools (llm/core.py: tools=[]), and the agent writes each call as JSON in its reply. tool_mode is already a version setting, but json is its only value. v3 sets tool_mode: native (built with milestone 1, so there is no separate version for it). For such a version the core passes the conversation's tools to the SDK as definitions, stops at the model's first tool call, and returns every call in that reply to tau2 without running any. Versions on json take today's path unchanged, which a test pins byte for byte. A native agent is only offered the tools it has, so a locked discoverable tool can't be called by its bare name: P4's 30 bare calls in v1 and 86 in v2 have no way to happen.

  • The probe first: one model call, as make judge-probe proved the judge's output format holds under the sealed core. If the subscription's CLI won't hand a tool call back unrun, milestone 2 stops there, and you hear why before anything else is spent.
  • Then the same 20 tasks. Checks: 0 slipped calls, 0 bare discoverable calls, more than 1.0 call a turn, and Fig 5's bar against v3.

Milestone 3 · banking's own optimiser writes the rules (P1, P2, H1, P4)

The project's rule is that a prompt changes through the loop, not by hand. So the rules go into banking's optimiser profile (§5), and make loop writes v4 from v3, the champion:

  • P1 research first: list every product and operation in the request, search the customer's stated problem before generic gates, and read each operation's procedure, eligibility and fee documents before unlocking anything.
  • P2 the four failure modes: check a customer's claim with a read tool before acting on it, check each request's preconditions against the others, and ask a neutral question rather than assume.
  • H1 the identity note: already done. v3 carries it as a setting (identity_note: true), and its runs made 0 account-email calls.
  • P4 as a rule: never name a discoverable tool without unlock-then-call, as v2's rule 7 did. A guard refuses a system.md that does.

v3 is champion, so a plain make loop DOMAIN=banking_knowledge CYCLES=1 starts from it, and the gate compares v4's test run with v3's.src/tau2_loop/loop/run.py: run_loop, run_cycle

Milestone 4 · the write-time judge (H3) — blocked on two of your rules

The judge learns from labelled checkpoints. Since 3 Oct its data is closed: a run scored after labels.CLOSED_AT, of any agent or domain, never joins the labels, golden answers or replays. Every banking run from v1's extension on is after that point. And no judge is replayed until you have confirmed its golden answers. So milestone 4 needs you to reopen the judge's data for banking. It would then be planned on its own page: J0 labels (no model), golden answers you tick in Review, and only then a replay.

5 · An optimiser per dataset — each tuned on its own, today's behaviour as every default

Today there is one optimiser: one prompt, one surface guide, one routing table, one set of budgets. The model and mode come from the command line. Only the data it reads differs by dataset. Milestone 0 gives each dataset a profile the loop reads before every cycle:
