1 · The finding that shapes everything

There is no holdout server. The leaderboard is self-reported, and every task is public.

I read the submission guide, the CLI that implements it, one real submission on the public bucket, and the hyper-τ-bench repo. The "submission page" is a pull request; the "holdout" is a choice we make ourselves.

What the board scores

All base tasks, ≥4 trials, self-run

You run tau2 run on every task in a domain's base split (airline 50 · retail 114 · telecom 114 · banking_knowledge 97), ideally 4 trials, with one agent model and one user-simulator model held constant. The board ranks per domain; a single-domain submission is allowed.

Source: vendor/tau2-bench/docs/leaderboard-submission.md §Requirements.

How it gets there

tau2 submit prepare → validate → PR

prepare reads the run's results.json files, checks format / all tasks present / trial counts (no model calls), computes pass^1…4 and mean cost, prompts for metadata, and writes submission.json + trajectories/. You commit only submission.json under web/leaderboard/public/submissions/<model>_<org>_<date>/, add the name to manifest.json, and link the trajectories (Drive / HF / release) in the PR. A maintainer uploads them to S3; taubench.com reads S3.

What that makes us

A custom, likely unverified entry

Our system prompt is written by the optimiser, tool calls go through a JSON contract instead of native tool use, and the user simulator is Haiku on the subscription rather than gpt-5.2. Under the guide that is submission_type: "custom" with modified_prompts: true and full methodology notes. It still lands on the board — flagged, per domain, comparable on task set and evaluator, not on protocol.

3 · What "held-out" means for us

The loop has seen 20 of each domain's tasks. The honest holdout is everything else in base.

Every promoted prompt was written by an optimiser that read traces from the 20-task train split. The board does not care (it scores all of base), but we should: a submission run gives two numbers, and the second is the one that tells us whether the loop generalised.

4 · Which domain, and what it costs

Airline v2 × 4 trials is the only full-domain, 4-trial submission that fits in ~2–3 subscription windows

Token use per conversation is measured from our own results.jsonl (agent + user simulator, Haiku). A 5-hour window was measured at roughly 15 M Haiku input and 1.6 M Haiku output before it locks; output is the binding constraint for the chatty domains. Estimates are ±50 % — the judge calls and per-window variance are not in the per-conversation numbers.

Recommendation

A — airline v2, 4 trials

It is the one option that produces a complete, board-shaped submission inside this branch's budget, and it answers an open question from s01 (N-3: is airline v2 a real improvement?) with 200 conversations instead of 20. Ledger records v2's full-base and held-out pass^k; the same command is then reusable for B/B′ later.

If the story matters more than the budget

B — telecom v1, 1 trial

Puts the promoted agent on the board. Costs the same windows as A but gives pass^1 only, and telecom conversations are 4× the tokens, so the run is slower and more exposed to window resets. Pick this if "the loop's winner on the leaderboard" is the point.

Either way

One domain, then stop

The guide allows single-domain entries and ranks per domain. The second domain is a later branch with the same command; nothing here is airline-specific except the choice.

5 · Build

Six steps: run, prepare, publish, record, show, write up

Everything model-facing stays on the subscription through the existing adapter. Nothing under agents/ is touched — a submission run is an eval of an existing version, not a cycle. The submodule stays at 2174a60; we import its functions, we never edit it.

S0eval

tau2loop eval --split base --trials 4 --resume <run_id>

split_ids() gains base (tau2's own split, all ids in tau2 order — no reshuffle). RunMeta.split = "base". run_eval accepts resume: reuse an existing run folder, pass auto_resume=True in TextRunConfig so tau2's checkpoint skips finished (trial, task, seed) tuples; traces/results are rebuilt from the whole checkpoint at the end. summarise() gains an optional subset so heldout.json can be computed from the same rows.

Ops: run under caffeinate -i (the process must outlive two window resets), concurrency 3, scripts/loops.sh gets a submission entry that restarts with --resume if the process dies (memory pressure has killed long jobs on this machine twice).

Tests: split_ids(d, "base") equals tau2's base list; resume skips done tuples on a dry-run folder; summarise(rows, subset) matches a hand count.

S1prepare

tau2loop submit prepare <run_id> → submissions/<model>_<org>_<date>/

Non-interactive twin of tau2 submit prepare: loads tau2_results.json with tau2's check_and_load_submission_data, runs the public verify_trajectories checks, gets DomainResults from get_metrics, and fills the Submission pydantic model from a small submission.toml in the repo (model display name, org, contact, references) plus the run's meta (tau2 version, evaluation date, user sim, seed, notes template). Sets submission_type: custom, modified_prompts: true, omitted_questions: false, trajectories_available: true, trajectory_files naming per the guide. Writes submission.json, copies the trajectory file (redacted — it already is), writes heldout.json and PR.md (the PR body, with the trajectory link placeholder). Then shells out to tau2 submit validate and fails loudly if it does.

Naming. model_name tau2-loop · Claude Haiku 4.5 (airline v2 prompt), model_organization nmp-dsci (the "model" is the system; Anthropic built the weights — said in notes), submitting_organization nmp-dsci, dir tau2-loop-haiku-4-5_nmp-dsci_<date>. contact_info.email is the one place the account email is meant to appear; it comes from submission.toml, not from ~/.claude.json, and redact_tree skips submissions/.

Tests: a dry-run trajectory file with 2 tasks × 4 trials produces the expected pass^k; validate passes on the output; the account email never appears in trajectories/.

S2publish

tau2loop submit publish <dir> — trajectories to a GitHub release; PR body ready

Uploads trajectories/*.json as assets of a release submission-<name> on nmp-dsci/tau2-loop (public repo, so the link is public — matches "Google Drive, HuggingFace, institutional storage, etc."). Rewrites the placeholder in PR.md with the asset URL. Prints the exact steps for the fork: gh repo fork sierra-research/tau2-bench, copy dir, edit manifest, gh pr create --body-file PR.md. It never runs the PR itself; that is your call after reading PR.md, and the plan's decision form asks how far you want the code to go.

S3ledger

loop/<domain>/submissions.jsonl + data/leaderboard.json local row

One row per prepared submission: run_id, version + fingerprint, base pass^k, held-out pass^k (test / reserve), cost, status prepared → published → pr-open → merged, PR URL. tau2loop submit status lists them. The leaderboard snapshot gets our row with source: "local" so the viewer draws us on the same board (rendered with a "self-reported, custom" chip). This is the hook later cycles use: the champion's last full-base score is the number a challenger's cycle must beat before another submission is worth its windows.

S4viewer

Results tab: our row on the board, held-out beside it

Lands with s02 V1 (board comparison) rather than as separate work: the Results home already needs a leaderboard table; this adds the local row and a "Submissions" panel reading the ledger. If s02 is not built yet by then, a minimal /api/submissions route and a table in the existing Results tab is enough.

6 · hyper-τ-bench

A different benchmark: it scores the developer that builds an agent, not the agent

sierra-research/hyper-tau-bench (τ^τ-bench, arXiv 2609.04611) wraps an outer loop around τ³-bench: a coding agent (Codex, Claude Code, OpenCode…) is dropped in a sandbox with evidence — policies, transcripts, call recordings, screenshots, an API with deliberate defects — optionally interviews a simulated client, and must ship a runnable agent. That agent is then scored on the τ³ inner loop. The "held-out" tasks it talks about are the 53 construction tasks in data/tau2/hyper/tasks/ — public in the repo, run locally by a sealed runner; there is no scoring server here either.

Shape

53 tasks · 4 domains

airline_plus 6 · retail_plus 6 · telecom 6 · banking_knowledge 35. The _plus policies are rebuilt so memorised τ-bench policies don't transfer. Reward = the built agent's pass rate; also reports build minutes, build cost, and a serve-credit ratio.

Submission

Also a PR, also self-run

web/leaderboard/public/hyper-submissions/<harness>_<model>/submission.json with per-domain scores; maintainers may rerun a sample. Six entries today, e.g. claude-code_claude-opus-5: overall 23.9, airline 55.9, retail 72.8, telecom 48.2, banking 5.9.

Why not this branch

Needs Docker + OpenAI keys; scores the wrong thing for us

User simulator, judges and client simulator run on OPENAI_API_KEY/OpenRouter, the construction sandbox is a Docker image, and the thing on the board would be "Claude Code with Opus 5", not tau2-loop. Interesting later: our optimiser is a developer of a kind, and the hyper-τ harness adapters are pluggable — a "tau2-loop as developer harness" experiment is a real follow-on, but a separate plan.

7 · Risks and open questions

What can go wrong, and what I have assumed

R-1 · window arithmetic

The 15 M / 1.6 M per-window figure is one measurement

If the real cap is half that, A takes 5 windows, not 3. Mitigation: S0 resume + the loop script; the run cannot lose work at a reset, it can only take longer. First window's throughput is logged and the estimate refreshed before window two.

R-2 · resume semantics

tau2's checkpoint compares run config

try_resume diffs the saved config and, with auto_resume, continues anyway but logs the diff. Our config must be byte-identical between attempts (same version fingerprint, seed, ids order). The test in S0 covers it with a dry-run folder.

R-3 · what the board sees

claude-sdk/claude-haiku-4-5 as the model string

get_metrics reads model and user-sim from the trajectory info. submission.json carries our display name, but the trajectory file will say claude-sdk/…; the PR notes explain the adapter. Acceptable; maintainers see odd model strings regularly.

R-4 · custom + unverified

The entry will carry a caution icon

Modified prompts ⇒ unverified by the guide's definition, regardless of trajectories. Fine for the goal (a comparable number on the same tasks and evaluator), but not a "Haiku 4.5 scores X" claim — the notes say exactly what the system is.

R-5 · sampling

The SDK exposes no temperature

tau2's default is 0.0; ours is the CLI default (RunMeta.sampling already records this). Stated in notes. It also means 4 trials measure real variance, which is the point of pass^k.

R-6 · airline v2 might not hold

16/20 on train can be 55 % on base

That is a finding, not a failure: the held-out split shows whether v2 generalised, and the ledger records it. If v2's held-out is below v0's 12/20 rate, the s04 page says so and the submission still goes in as the loop's honest result (or you choose not to open the PR — the form below asks).

Assumptions I made without asking

  • The user simulator stays Haiku on the subscription (the guide allows any user LLM; it is reported on the board). Switching to gpt-5.2 would need an API key and per-token billing — out of scope.
  • Trajectories are hosted as a GitHub release asset on this public repo rather than Drive/HF — public, versioned, no new account. Say so if you'd rather use Drive.
  • The account email goes into contact_info from submission.toml; nothing else in the submission carries it.
  • submissions/<name>/trajectories/ is gitignored (20–40 MB per domain); submission.json, heldout.json and PR.md are committed.
  • No banking, no second domain, no s02 viewer work beyond the minimal submissions panel, in this branch.
