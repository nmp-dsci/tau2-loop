Investigation · v7 and v4 on banking's train and test splits · every failed conversation replayed, no model

Nine v7 conversations made every gold call and still failed: what they did besides broke them

Banking's reward is the database check. tau2's action check asks only whether each of gold's calls was made, so a conversation that makes all of them and one write more scores 100% of actions and 0. That happened in 6 of v7's 23 failed train conversations and 3 of its 25 failed test ones. Each extra write traces to a decision the agent made: in task_036 it offered a dispute the customer never asked for, and the card-digits tool followed from that. The fix is one rule for every job, the customer's job first and its checks before its writes, not a guard per failure.

04 · Why 100% fails — the action check never sees the rest

Fig 4 · task_046, scored twice

recallThe action check is recall

Each gold call is matched to a call with the same tool and arguments; anything else the conversation did is not looked at. It is the “gold actions captured” number in s17 and Evals.

exactThe database check is exact

The final database is hashed and compared with gold's. An extra payment, credit, transfer, dispute, or a tool given to the customer (tau2 records each gift) changes it.

errorsAn errored call still counts

The action check does not ask whether the tool succeeded: task_053's two approvals both returned an error and both matched gold. 6 of v7 train's counted calls and 23 of v4 train's had errored.

100% of gold's actions means nothing was missed, not that nothing was added; s17's “gold actions captured” is read with that in mind.

06 · Fixes — one rule for every job, not a guard per failure

Fig 6 · proposed fixes, by kind · G1–G3 of the earlier draft are dropped
fixthe changecatchesbuild
F1 · The customer's job first, its checks before its writesroot cause · one agent rule for every jobChoose the job from what the customer asked for; when the customer reports a problem without asking for an action, ask which action they want. Finish the job's checks, looking up what each needs, before its first write. Give a user tool only when the customer wants that action: tau2's own policy, “Only give a tool when the user would like to perform an action”.tau2 policy, Giving Discoverable Tools · the knowledge base's procedurestask_036 (the job) and task_046 (the checks), on v7 and v4● recommended

Dropped, as your note says, because each was fit to one failure: G1 named one tool and one protocol for task_046, G2 one order for task_053, G3 a calculator for two conversations of one customer. F1 is not a hook: “the customer named a dispute before the agent did”, checked at the write, would send back 4 passing v7 train conversations and 3 on v4, cash-back disputes the agent was right to offer. task_053's order and task_020/027's count stay open.s19/offered.py · s19/wfdo.py

F1 is one rule for every job, drawn from tau2's policy and the procedures' own order; F2 makes the workflows carry it.

07 · v4 too — the same writes, so the workflows did not start them

Shared with v4

  • task_036: v4 also offered the two fraud disputes before the customer asked, and filed them; without its extra writes, it passes.
  • task_046: v4 also paid the balance; without the payment, it passes.
  • task_053: v4 also made every gold call and failed; on test, v4 denied a credit-limit request that gold never denies.

v7's own

  • task_063: the transfer followed the Sonnet customer's claim that its $8,000 was in checking; v4 played it with a Haiku customer.
  • task_020 and task_027: v4 failed both on its customer writing the disputes as text (s18), so it never reached the count.

v4 made the same decisions with no workflows, so the fix belongs in the agent; in v7 the dispute workflow then carried the wrong job through, so a v7 fork needs workflow_rag r2 as well.
