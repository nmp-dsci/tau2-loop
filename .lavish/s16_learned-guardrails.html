Mine the RAG into deterministic rules?

Yes. ToolGuard (IBM, EMNLP 2025) did this on τ-bench airline. It compiled the policy into a guard per tool once, offline, then ran each guard before the tool call: pass^1 went from 0.450 to 0.685 on 22 policy tasks. The model writes a rule once; after that the same inputs always get the same verdict.

To read: ToolGuard paper (Zwerdling et al., arXiv 2507.16459) for compiling policy into guards; AgentSpec for rules kept as data; Agent Workflow Memory for workflows learnt offline; ByteVerity's METHODOLOGY.md (PR #385) for the banking version of all three. More in sources.

A separate agent that researches and sets the rails?

Yes, and better done offline, as you suggested: approach D. A RAG agent works through the documents and the train questions once, before any run, and writes one workflow per kind of job. The live agent identifies the job and looks its workflow up; the harness enforces the steps. Nothing is researched while the customer waits. Approach B is the live version: one extra session per conversation, and a plan that differs from run to run.

Kept up to date, without overfitting?

Rules come from document sentences, not from failures. Every rule is replayed over every train conversation; any rule that fires on a passed one is rejected. After each new train run the replay is repeated, and rules that start to misfire are retired.

What does the top custom agent do?

ByteVerity's engine makes 711 of its 820 writes and passes 182 of 240 conversations on our train tasks, against Qwen's 132. The model talks; fixed drivers decide and write. Its general checks were logged but never acted, and part of the lead comes from drivers fitted to public tasks. How the engine is built.

Every workflow it writes is cached, and v6 looks up the one each job needs. The customer-step ledger is one of those workflows. Build and test — a golden set measures the RAG agent; every workflow it writes is cached, and v6 looks them up

The question is whether agentic search can take a customer's question, research the documents and produce the right procedure: the tool calls that get the task to pass. A golden set answers that with a number instead of an assumption. The number measures the RAG agent and shows where to improve it. It does not decide what is cached: every workflow the RAG agent writes goes into the library, and v6 looks up the one each job needs.

"100%" is measured, not assumed, and the measure is not a filter. Every workflow the RAG agent writes is cached. Dropping the ones that miss gold would select on train answers, and on test there is no gold to select with. The train ceiling is below 60: task_053 and task_083 cannot pass as graded, and task_082 is in doubt.

In the dry run the RAG agent reads the customer's whole train script, so this scores procedure knowledge, not how well the agent asks. The asking is scored when v6 plays. tau2 builds its expected database by running gold's calls on the starting database; the dry run runs the RAG agent's calls the same way. Running it in our own code, not by editing the vendored tau2, is the first thing the build has to prove.

A workflow worked through — a card recommendation asks before it answers, and the questions are part of the workflow

A workflow is not only tool calls. Before a card can be recommended, the agent needs facts the customer holds back until asked. In task_001 the script says to mention the Rho-Bank+ subscription "ONLY … if you are asked", and in task_002 not to bring up the monthly spend unless asked. So the workflow lists what to ask and why, the eligibility rules that drop a card, how to decide among the rest, and who takes the action.

Workflows as skills — a good fit for how the agent loads them, as long as the harness still enforces the steps

A skill is a folder the model loads when its one-line description matches the task. Only the description sits in context until then, so 23 workflows cost a line each rather than 23 procedures in the prompt. Each cached workflow can become one: a SKILL.md that tells the model when it applies, what to ask and how to decide, beside the workflow.json the harness enforces. When the model loads a skill, the job is named.

ToolGuard — use its accuracy checks on the RAG agent's workflows; its guards cover the writes, not the steps the agent skips

“Towards Enforcing Company Policy Adherence in Agentic Workflows” (Zwerdling et al., IBM, EMNLP 2025 industry track, arXiv 2507.16459) works in two phases. At build time, offline, it compiles the policy documents into guard code, one guard per tool. At run time, each guard runs just before the agent calls its tool. If the call breaks a policy, the agent is told which one and asked to revise. It is approach A, published. Its value for building banking workflows is how it checks that what it compiled is right.

The four steps in words
  1. Elicit the facts only the customer has: a reason, a preference, which transactions.
  2. Bind them to the accounts, cards and transactions the tools returned, and to its own earlier receipts.
  3. Decide the policy question from a decision table compiled from the documents: 3,672 clauses, each citing its source, taken from the 698 public documents.
  4. Execute the write itself once the authorisation, arguments, eligibility and earlier steps are all grounded. If a case is ambiguous or not covered, it goes back to asking the customer or hands over to the model. A driver never invents a preference.
two enginesValidity · Synthesa

Validity: decision tables, entity-keyed progress ledgers, prerequisite and authorisation checks, idempotent writes; it corrects or blocks a write whose arguments conflict with what the tools returned. Synthesa: policy answers bound to evidence, referral and PIN-lock plans, a dispute write fence.

  1. A clause store, compiled once. All 698 documents split into 3,672 clauses, each citing its source and pinned by SHA-256 to one tau commit. How the clauses were extracted, by hand or by a model, is not published.
  2. A controller per procedure. 53 families fire on train, each versioned (.v1), each a state machine through named stages. Account opening, for example: identity_prompt → lookup_user → get_current_time → log_verification → read_accounts → collect requirements → recommend → open → close → completion.
  3. A record on every engine turn. The tool it emitted and the arguments; a source line naming the documents and the facts the step rests on; and the obligations still open. The job cannot complete while one is pending. "PROVEN" marks a decision the Synthesa side computed from those facts.
  4. A turn loop. Read the facts from the conversation and the tool results. If a controller owns the current state, it writes the turn itself, a decided call or a set message, with no model call (1,664 turns on train). If not, DeepSeek writes it, and the general checks below watch.
  5. A ratchet, offline. Replay a failed conversation and find where it first went wrong. Add a rule that does not name the task, with negative controls. Rerun the driver gate, then all 97 tasks, then the four-trial run. Their methodology says this was done on the public tasks.

The four steps in words
  1. tau2 asks the agent for its next message. DeepSeek sits inside that agent, behind the engine.
  2. The engine looks first. From the facts so far (the request, the verified record, what the tools returned, what is still pending) it decides whether a controller owns this state. The engine turns carry only the engine's own record, apart from 19 where it replaced a reply DeepSeek had written.

  4. tau2 runs whatever comes back. The environment cannot tell an engine turn from a model turn. tau2 keeps the transcript, so the engine's turns will normally reach DeepSeek's next prompt as its own earlier messages. Is the engine what the RAG agent builds? — No: the RAG agent writes the workflows, and the engine that runs them is code written once

ByteVerity's agent class holds two things in one place. One is the procedures: a controller per family, with its stages, what to ask, how to decide and which write ends it. The other is the machinery that runs them: claim the job, take the turn for a decided step, track what is pending, replace a reply that skips a step. Engineers wrote both, one procedure at a time. v6 pulls them apart. The procedures become data, a workflow.json per job, written offline by the RAG agent from the documents and scored on the golden set. The machinery becomes driver.py: generic code, written once, that reads whichever workflow was named.

The workflow marks who takes each step, which is the contract between the two halves. A do step with a call and arguments taken from records (verify, read the transactions, give the customer a tool): the driver makes it. An ask: the model asks the customer for a listed fact it does not have yet. A decide (which transactions are wrong, which card fits the customer's spend): the model decides, and check_write checks the write that follows. A step by the customer: the ledger tracks it until it is done. The RAG agent writes these marks with the steps; the driver only reads them.

So a miss is fixed in a different place. In ByteVerity a wrong procedure is an engineer's edit to the class. In v6 a train miss is read to improve the RAG agent, which rebuilds the whole library, and driver.py does not change: a new job is a new file, not new code. That holds only while the driver stays generic. A driver that names a job, a product or an amount has become ByteVerity's scenario driver, so the build tests it on every workflow in the library and on a made-up workflow for a job that does not exist.

# agent/driver.py: a sketch, not built. It reads the
# workflow as data; it names no job, product, amount or id.

def next_step(wf, facts, led):
    """The next step the harness takes itself,
    or None: the model writes this turn."""
    for step in wf["steps"]:
        if step["id"] in led.done:
            continue
        if any(a not in led.done
               for a in step.get("after", [])):
            return None
        if step["by"] != "harness":
            return None      # ask, decide, customer
        if "compute" in step:  # a quoted rate table
            found = facts.evaluate(step["compute"])
            led.items = {k: "open" for k in found}
            led.done.add(step["id"])
            continue
        args = facts.fill(step.get("args")
                          or step["args_from"])
        if args is None:
            return None
        return ToolCall(step["call"], args)
    return None


def on_tool_result(call, result, led):
    """Done only on a tool result, never on
    what anyone says."""
    led.mark(call, result)


def check_reply(text, led):
    """While items are open, the reply must
    hand over the next one by its id."""
    open_ = [k for k, v in led.items.items()
             if v == "open"]
    if open_ and open_[0] not in text:
        return (f"{open_[0]} has no tool result. "
                "Ask the customer to run it now.")
    return None

  • Drivers that own a procedure's write, not checks that watch it. ByteVerity's general checks never acted; the drivers made 711 of its 820 writes. If v6 builds rules, the ones that carry weight drive a procedure step by step, with a fallback to the model.
  • Procedure families as the unit the miner writes. Disputes, cash back, retention and closure, lost or stolen cards, referrals, card applications and fee refunds recur across 3–10 train tasks each, and each maps to a procedure document.
  • Scenario drivers. A rule that names its answer fits one public task, and the account-opening driver does this across 8. This is where much of its lead on "judgement" failures comes from.
  • Trusting a driver blindly. On credit-card disputes, retention, lost cards and credit limits the drivers score below a stock agent. Each driver needs the same replay gate as a rule.
  • Coaching the simulated customer on the harness's tool-call syntax. It works on the benchmark, but it tests the simulator, not the agent (Q7).
  • The debit-dispute wall. 6 train tasks where ByteVerity passes 3 of 24 and both leaders 0 of 24. Stop spending effort on it.

The risks in words
  • A deterministic mistake repeats. Mitigations: block once and then allow (the existing _once), the replay gate, and a review page where you tick each rule.
  • Sparse validation. 29 passed train conversations exercise only some rules. A rule that never triggers in replay is unproven, not proven safe; the page reports it as "untested".
  • Gold disagrees with the documents in some tasks (task_082 closes a card the document says to reissue). Mining follows the documents, and such tasks stay marked as task faults.
  • Trajectory drift. The B check passed replay on v4's conversations, then fired in v5's task_044, which took a different path. The replay is repeated on each new train run.
  • Not stock. All four approaches deviate from the leaders' single-loop agent, as v4's checks already do.
