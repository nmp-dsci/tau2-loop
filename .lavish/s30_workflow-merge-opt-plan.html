01 · Today — a free rewrite per merge, checked one step at a time

This is the first drawing of the pipeline as the code runs it. One session researches one customer's script, drafts the jobs it found, then merges each draft into the library job for the same procedure, in the same conversation. Code checks what it wrote, a reviewer reads some steps, and the library takes the result. The answering agent sees only the result.

Fig 1 · workflow_rag today, from a customer's script to the grader · hover any box for the code it is

The red pins mark where a wrong step gets in or a right one gets out; they are listed below. Each session saves events.jsonl (every turn, tool result, harness message and review) and output.json (draft, decision, and the merge records: changelog, checks, failed, settled, review); each library keeps commits.jsonl. Read from rag_agent.py (run_session, _merge_concurrent, _assess, _send_back, _settle, _take), library.py, provenance.py and rag_agents/banking_knowledge/r19/.

  1. A conflict is settled by which side wrote the step, not by the document. r18 kept the library's step unless the merge named a change: 090's draft defined the suspicious period, and the merge kept r17's undefined one (s25). r19 says the draft wins, and the merge still overrode it: 088's draft said "count from the statement date", and the merge rewrote the $50 tier to count from when the customer noticed, which gold contradicts. 086 did it again.
  2. A dropped step is logged and forgotten. r19's code writes what a merge left out into the changelog and takes the job. Its 44 taken merges removed 569 old steps, and 117 of them took their only quote out of the job (s26). In the debit job that included the step that files the dispute.
  3. The reviewer reads one step against its own quote. Code picks steps by four text flags, and the reviewer sees each picked step's quotes with 250 characters either side. A rule that follows from two passages reads as unsupported: "the quote only defines the category; it gives no amount calculation" (r19 088, on the overcharge rule).
  4. The merge is one free rewrite at the end of the research. The merge turn carries the whole research conversation, 208K to 333K characters, and writes each job again in full, up to 50K characters for this one. Nothing holds it to its inputs: in 088 and 086 it changed the draft's own liability rule, and in 088 it dropped a right category rule because it sat in one step with a vague line.

04 · The target — the document decides, whoever wrote the step

A right merge keeps every step the documents back, removes every step they do not, and writes the result in the procedure's order. It never asks which side a step came from. To do that it needs one more standard than today's reviewer has. Today a clause is either one quote's or unsupported. A right merge also needs "derived".

05 · Three merges to test — from one added rule to a rebuild

The three options differ in how much of today's merge they keep. A adds one rule to r19's. B splits cleaning from merging, so a wrong old step is removed whatever the draft says, and a right one is protected. C stops rewriting jobs as one block: it breaks both versions into claims, settles each against the documents, and writes the job again from the claims that survive.

option A · r19 + one rule · s26's r20

Account for every quoted step

r19's merge (draft as base) plus one code check: each old step whose quote is found must be carried, named as covered by a new step id, or named as replaced by a passage. An unaccounted one sends the merge back once; still unaccounted, it is carried over as it was.

what it leaves

small: rubric.lost already lists the drops; _settle gains a send-back, merge.md one paragraph

option B · two calls · separates cleaning from merging

Audit the old version, then merge

First an auditor, in its own context with no draft and no research, reads the library's version step by step with the full passage each quote comes from, and marks each step valid, rewrite (to what the passage says) or invalid (unfound, unsupported, contradicted). The merge then takes the audited version and the draft. A valid step may leave only when the merge names the draft step that covers its case; a conflict between a valid step and the draft is settled by quoting the passage that decides it.

model calls per merged job
+1 auditor call per merged job (reviewer-sized, cacheable per job version); merge as today

option C · three calls · rebuild the job from verified claims

Claim ledger, then rewrite

Both the library's version and the draft are broken into claims: case, field or action, value, quote, doc. Code groups claims by case and field and flags a slot with two values. A verifier, in its own context with the documents, marks each claim supported or not and settles each flagged slot by its passage, or makes it a question for the customer. A writer then writes the job from scratch, in the procedure's order, from the surviving claims. Code checks that every surviving claim is in exactly one step, no rejected claim is, and no slot has two values.

model calls per merged job
+3 fresh-context calls per merged job (extract, verify, write); no research conversation in the merge
what it fixes
all four defects by construction: nothing is kept or lost by origin, conflicts are slots settled by passages, the job is rewritten, every clause is verified. A step that mixes a right clause with a wrong one is split, not kept or dropped whole (088 lost the cloned-card rule that way)
what it leaves
claim extraction can split or merge a rule wrongly; the step order and the tool parameters (D9) must be rebuilt; the most to build
to build
large: three prompts, a ledger schema, slot grouping and coverage checks in code
prediction on the debit job, before it runs
K1, K2 and K8 survive as claims, and T1 meets the statement rule in one slot, where the passage decides; the risk is the rebuilt filing step missing an argument (D9) or the order
What all three share

The derived standard

B's auditor and C's verifier judge each clause as stated, derived, a question or unsupported, with the full documents a step cites rather than 250 characters around a quote. A derived clause must write out its steps, and the checker follows each one. A can take it too, as a change to review.md.

Two code checks every option gets

A tools entry that names a step the job no longer has fails (r19 v3's filing tool points to a removed f_file). A write tool the job lists must have a step that calls it with every argument, or a not_used reason.

The same inputs

Each option merges r18's four saved drafts into r17's version, in r18's lock order. No research runs, so a difference between options is the merge's alone.

A is the control: s26's proposal, cheap to build. B and C are the two ways to stop settling steps by who wrote them. The eval in §06 decides between them.

06 · The eval — an answer key the merge never sees, then a play

A merge is scored on the job it writes, before any conversation is played: does the job lead the agent to the facts gold's filings need, and is it free of the wrong rules found before? Then the best versions are played. The answer key works like the test split: it is the grader's, and no prompt the merge reads contains it.
