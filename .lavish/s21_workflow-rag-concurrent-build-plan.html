Research together; lock only the workflows a merge writes

r2 builds its library one question at a time, because each merge must start from the version the last one left. A real deployment takes questions as they come, several at once. Your idea holds, with two refinements. Research never reads the library (4.5 minutes, the median of 30 sessions), so it needs no lock. A worker locks only the workflows it is about to write. It holds the lock while it merges (2.9 minutes), and it merges into the newest version, so a commit made while it worked is picked up, not overwritten. A shared lock table tells every worker, and you in the viewer, who is updating which workflow. Replayed on the 30 sessions with 4 workers and a shuffled queue, the build takes 1.21 hours against 4.22 one at a time.

Recommended: D, with a shuffled queue

Every merge reads the newest version after it holds the lock, so r2's merge prompt and its D8 gate apply unchanged and nothing is ever re-merged. It is within 4 minutes of E at 4 workers. The lock table it needs is also the answer to “is another worker updating this workflow?”.

Why not E

E skips the decide turn but merges against a version that may be gone by the time it commits: 11 of 30 in id order, about 4 of 30 shuffled. Each re-merge is a model merging three versions it half wrote, a new failure mode for D8 to catch. Worth it only if waits grow, at 8 workers and beyond.

04 · One worker — research free, lock late, merge newest

Fig 4 · one worker's turn on one question · hover a stage for its rule
  1. Research as r2 does now: no lock, any number of workers at once.
  2. Decide: one short turn with the snapshot's candidates in front of it, replying {"drafted job": ["library job", …] or []}. A new job's own name is locked too, so two workers cannot create one procedure twice.
  3. Lock every job it will write in one call, sorted. If any is held it holds nothing, joins each job's line, and logs who is in the way (wait event). A heartbeat thread renews the lease every 30 s while it holds it: one merge turn can run 7.9 minutes without a single event (the longest of 30).
  4. Read newest: each locked job's head now, so a version committed while it researched or waited is the one it merges. This is the “update with the new file” step, and it is free: nothing has been written yet.
  5. Merge with r2's merge.md, unchanged, showing the newest versions.
  6. Check: rubric.gate against the newest versions (D8, D1). A job outside its lock is refused here and sent back once with the others.
  7. Commit: each version's parent must still be the head and the lock's token still current, or the store refuses it. Only a holder whose lease expired can hit this; it then locks again from step 3.
  8. Release in a finally, so an error never leaves a job locked.

07 · Failures — crashes expire; stale holders cannot commit

A worker dies holding locks

Its lease runs out within 120 s of its last heartbeat and the next worker in line takes the jobs. If the dead worker comes back and tries to commit, its token is stale and the store refuses it (a fencing token).

Deadlock

None: a worker asks for all its jobs in one call and holds none while it waits, so no two workers can each hold what the other needs.

Starvation

Each job serves its waiters first come, first served, so a worker that needs two busy jobs is not overtaken forever by workers that need one.

Renamed while waiting

A merges X into Y and retires X; B was waiting for X. On the grant, B resolves X through its alias to Y, sees it does not hold Y, and asks for both again in one call.

A merge writes a job it did not lock

The gate refuses that job and sends the merge back once, naming the jobs it holds. Refused again, that job keeps its version, as r2 keeps the previous version today; the question's case waits for a later merge.

Two new jobs for one procedure

A new name is locked like any other. After the grant, the worker ranks its new job against jobs committed since its snapshot; a match sends it to merge into that job instead. Rare: 1 new job in 30 sessions.

The answering agent reads mid-build

find_workflow reads committed heads only. A merge in progress is invisible until its commit, so v6–v8 never read a half-written workflow.

08 · Shared state — files now, Postgres for many machines

FileStore · one machine

  • rag_library/<domain>/<rag>/commits.jsonl: one line per committed version (job, version, parent, session, task, retired names, time). Append-only, in git, like rag_agent_runs/; the library replays from it.
  • …/locks.json: held and waiting locks. Runtime only, git-ignored.
  • Each call takes fcntl.flock on …/library.lock plus a thread lock, for milliseconds: enough for the build's threads, a second build process, and the viewer's own sessions.

PgStore · many machines

  • workflow_versions (job, version, parent, body, session) and workflow_heads, moved by UPDATE … SET version = $new WHERE job = $j AND version = $parent: a compare-and-swap.
  • Lock rows with an expiry and a token from a sequence; or pg_advisory_xact_lock for the short commit itself.
  • The question queue taken with SELECT … FOR UPDATE SKIP LOCKED.
  • Per the platform contract, a tau2-loop database is declared in nmp-central-ai's registry/projects.yaml and made by make db-init first. None exists today.

Gap 1 · the harness's messages
Write each message the harness sends as a user event: the merge message in full and every nudge. Then a session's conversation rebuilds turn for turn, with nothing inferred. It is a few lines in run_session and _merge.


Gap 2 · the order of writes
One at a time, start order is commit order. With several workers it is not, so commits.jsonl (C1) records every write: job, version, parent, session and lock token. The library as of any write is the log up to that line.



What a replay is for



The library at any write
Rebuild the library as of any commit; read a job's history version by version, with the question and the changelog behind each change.


Merge again, research once
Take a session's research, its events up to the draft, and merge it against another library state: another order, the concurrent build, a new merge prompt. That costs one merge (median 2.9 min) instead of a whole session (median 7.7 min).


r1's saved work
The same re-merge folds r1's 118 saved workflows (from 62 sessions) into one per job, with no research. That is the question you asked in chat; it needs no locks, since different jobs never touch.




What a replay cannot do is make the model repeat itself: a re-run is a new sample. Replay means rebuilding exactly what happened, then asking again from any point.rag_agent.py run_session (model and tool events) · _merge (merge, note, merged events) · output.json draft

12 · Risks — order, the decide turn, throughput, the pause




The library depends on order
r2 merged in id order; r3 merges in whatever order commits land. commits.jsonl records it and the shuffle seed is kept, so a library can be rebuilt and two orders compared. C7 compares r3's library with r2's on the rubric.


The decide turn can be wrong
If the merge wants a job it did not lock, the gate sends it back once. How often that happens is a number C7 reports; often would mean deciding on full versions instead of the snapshot's.


Subscription throughput
4 Opus sessions at once is about the load of v7's train and test runs side by side (6 conversations). The replay assumes no throttling; C7 measures it.


The paused build
r2 stopped at 34 of 60 on your call, and v8 has not run. Nothing runs from this checkout now, so the work can go on this branch. task_064's session was stopped two minutes in; the library ignores it and the question runs again.


The replay is an estimate
It reuses what each session wrote alone. Run together, a session sees a different library and may write other jobs. It is good enough to rank the designs, not to promise minutes.
