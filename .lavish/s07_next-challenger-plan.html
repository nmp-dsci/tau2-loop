3 · Promotion — your rule is the gate today; trials change pairing

promote if(a) any increase with 0 regressions — at least one task fixed and none broken (DOMINANCE_MIN_FIXED = 1); or (b) one-tailed significance — exact one-sided McNemar on the discordant tasks, p < 0.05 (ALPHA). elsehold; the challenger stays registered, its folder and run stay in the repo, and the next optimiser session reads why. thenthe challenger runs the test split too, promoted or held, and champion vs challenger on test — fixed, broke, p — is reported next to the verdict. It never decides: your standing rule is that the test split is reported, never optimised on, and a gate that read it would be optimising on it one step removed. sourcesrc/tau2_loop/eval/compare.py, unchanged since the s01 review; the ledger records which rule fired.

Takeaway: nothing about the rule changes. What changes is what a "task" is when a run has 3 trials, and how many tasks the test has to work with.

With 3 trials, a task's score is its pass fraction

Today compare() pairs rows by task#trial when trials > 1, which treats trial 2 of the champion and trial 2 of the challenger as a pair; they are two independent samples. Proposed: pair by task; a task's score under a run is its passes over its trials (0, ⅓, ⅔, 1); fixed is a task whose fraction rose, broke one whose fraction fell; accuracy is pass^1, the mean fraction. The test becomes the exact one-sided sign test on the tasks whose fraction changed, which is McNemar exactly when trials = 1, so the ledger's four historical verdicts read the same. At the 1 trial per task you chose (Q5) this is today's test to the letter; the fraction form is there for the day a run carries trials.

5 · Runs tab — pass^1·2·3, and every check with its denominator

Your question, answered. τ² scores a conversation as the product of the checks named in the task's reward_basis, and that basis differs by domain. "Expected actions" and "database matches gold" are not two checks that every task runs: the database check subsumes the actions in three domains (the gold database is what the expected actions produce), and the action check counts only where the basis says so. Environment assertions exist only in telecom. Airline tasks carry NL assertions in their spec, but τ² neither scores nor evaluates them there.

the window is the real budget

This account is default_claude_max_5x. Anthropic publishes no token figure for the window, but the runs measured it: three of the 13 committed runs (telecom v0, airline v2, telecom v1 test) took 233–243 minutes for 20 conversations against 10–34 for the rest, because the provider hit the 5-hour window and slept until it reset. Before each stall, 10–14 M tokens as the traces count them (prompt + completion, cache reads included, almost all Haiku) had gone through in about 1.2 h. Airline's experiment is about 10.5 M such tokens: 4 M for v3's two runs at v0's 60 k per conversation, 5.5 M for v4's at the optimised prompts' 110 k, 1 M for the optimiser session. That is 75–105% of one window in raw terms, and 90% of it is Sonnet, which the limit weighs about 3× Haiku if Sonnet 5 is priced like Sonnet 4.5. Expect the window to run out once or twice: the provider sleeps through a reset (about 3.5 h each time), and only a wait past 6 h, the weekly cap, turns the remaining conversations into error rows that make a run repeat. The schedule that avoids guessing: v3's two runs at the start of a fresh window, v4's after the next reset.

What stops the run

Each run is a folder and each registry write is a file, so every step is a checkpoint. The run stops for you if the smoke or a run shows a parse-failure count above zero (Sonnet through the JSON contract is new here), the service answers anything but 200 during the smoke, a run stalls longer than one window, or the gate breaks more than it fixes. Airline also answers whether concurrency 5 is tolerated, for the later domains.
