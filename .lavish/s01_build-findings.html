Four baselines, five loop cycles, one promotion — and two things the harness told the agent that it should not have

Everything s00 approved is built and runs on the subscription: the τ²-bench adapter, per-domain 20/20 splits, v0 baselines in all four domains, the optimiser loop with its McNemar gate, the viewer, the keyless demo image. The loop produced a real, gated improvement on telecom (14 → 19 on train, 19/20 on the held-out test split). Airline and retail each moved up on train (12 → 16, 14 → 16) without clearing p < 0.05. The most useful findings were not scores: the Claude CLI tells every child session today's real date and the account's email, and Haiku used both inside the simulation — the airline agent refused to touch flights because "today" was 2026, the retail agent looked customers up by the author's own address in 20/20 conversations.

1a · Review question — "let it through if it breaks 0 and fixes some?"

Statistically, no; as a decision rule, yes — and it is now in the gate as a second path

With zero breaks the one-sided McNemar p is exactly ½fixed: 3/0 → 0.125, 4/0 → 0.062, 5/0 → 0.031. Nothing short of five clean fixes clears 0.05 at N = 20, and no test can turn "we saw no regression in 20 tasks" into "there is none" — twenty clean tasks are consistent with an unobserved regression rate of about 14% (rule of three). So "no downside" is not something the train split can prove.

What it can support is a dominance rule: promote when the challenger breaks nothing and fixes at least 3, whatever p says, and let the held-out test run that follows every promotion carry the risk. Three, not one, because a single trial of Haiku flips tasks on its own — 1/0 and 2/0 are inside the noise. Implemented as compare.DOMINANCE_MIN_FIXED = 3; the ledger records rule: mcnemar | dominance so the two kinds of promotion never blur. Applied to this page's cycles: airline v1 (4/1) still holds, retail v1 (3/1) still holds, airline v2 (4/0) promotes. Its test-split run is the next thing to spend a window on (N-3, re-scoped).

02 · Walk-through

2 · Walk-through — what was built, in the order it happened

Each milestone as s00 §11 defined it, what it turned into, and the commit or folder that holds it. Times are Sydney, 15–16 Sep 2026.

M0scaffold

Repo, submodule, splits, viewer shell

τ²-bench v1.0.1 pinned at 2174a60 as vendor/tau2-bench, never edited; its data/ ships with it and resolves under the editable install. tau2loop splits draws 20 train / 20 test per domain at seed 300 and commits data/splits/<domain>.json plus a task extract (policy, tool schemas, tasks) the viewer serves offline. The FastAPI + React viewer is DABStep-loop's, re-tokened, with its own τ favicon; MLflow on :5601 so DABStep's :5600 store stays untouched.

M1adapter

Every model call on the subscription — proven on tau2's mock domain, 8/10

tau2 routes every model call through litellm. A litellm CustomLLM registered as claude-sdk/ answers each one with a single Claude Agent SDK query() on a private event loop; tools travel as a JSON reply contract in the prompt and come back as tool_calls, so tau2's orchestrator executes them unchanged. The NL judge is the same provider via a monkeypatch of tau2's default judge model. require_live() refuses to start with an API key present; tau2's own load_dotenv() walked up to ~/.env and injected one, so scrub_injected_key() now drops anything the shell did not have at start-up.

M2baselines

v0 on train in all four domains — after the harness finding in §4 halved the time and quadrupled retail

The first airline and retail runs (9/20, 2/20) were on the inherited harness: 47–56k input tokens per agent call, most of it connector tool schemas the CLI loads from the user-level claude.ai config. With strict_mcp_config and the session-title call switched off (DABStep-loop s02's finding), the same v0 scored 12/20 and 14/20. Telecom 14/20, banking 4/20. tau2loop promote registered each as champion; tau2loop gate replays every committed conversation through tau2's evaluators and agrees 80/80.

M3loop

Five cycles: airline ×2, retail, telecom; banking cancelled

make loop DOMAIN=… reuses the champion run by fingerprint, gives one Sonnet session the failed conversations condensed (transcript, unmet assertions, expected vs actual actions), lets it write only agents/<domain>/v(n+1)/ (PreToolUse hooks deny everything else and deny Bash running simulations; a tree checksum verifies afterwards), requires diagnosis.json, runs the challenger on train, gates, and appends the ledger. Telecom promoted and then ran the test split once. §3 has each cycle.

M4holdout

Test split run for the one promotion; README results table

Per s00, the test split is spent only on promotion, so only telecom v1 has a test number: 19/20, the same as train, with a different single MMS PERSONA:Hard task failing. The three held challengers have none, by design — their train gain is the only evidence and it is not significant. README carries the table above.

M4bfindings

This page

Every number here is read from runs/*/results.jsonl, loop/*/ledger.jsonl and workspace/*.log; the paths in each cell are where to check.

M5deploy

Keyless demo image builds and runs locally; App Runner needs one SSO login

The Dockerfile serves committed runs under DEMO_MODE=1 with no tau2, litellm or SDK inside, so it cannot call a model. Terraform for bootstrap (OIDC role, ECR, state) and the App Runner service, and the deploy workflow on main, are written. The one-off terraform apply in infra/terraform/bootstrap and the first image push need aws sso login --profile data-qa, which only you can run.

3 · What the optimiser did, cycle by cycle

Each card is one ledger entry: what Sonnet diagnosed, what it changed, and what the gate said. The diagnoses are Sonnet's; the "actually" line is mine after reading the same traces.

airline · cycle 1 · v0 → v1

12 → 15hold · p 0.188

Diagnosed: 7 of 8 failures were the same bug — the agent reasoned "the current date is 2026-09-15", so every May-2024 flight was "already flown" and it refused or transferred. The 8th declared flight duration unanswerable.

Changed: a date-grounding block in system.md; a helper.py whose extra_context re-states the policy's own "The current time is…" line at the end of the prompt (regex on the policy, no hard-coded date).

Gate: fixed 11, 22, 24, 44; broke 19 — the new caution added a confirmation turn and the user-sim stopped before the cancel.

airline · cycle 2 · v0 → v2

12 → 16hold · p 0.062

Diagnosed: the remaining four were multi-reservation lookups stopping after one, balances the agent would not sum itself, and the extra-turn regression from v1.

retail · cycle 1 · v0 → v1

14 → 16hold · p 0.312

Diagnosed: the first tool call in every failing transcript was find_user_id_by_email with an address "the customer never stated — it leaks from the agent's own context"; plus transfers for answerable questions, a mis-paired item swap, and "skip the exchange" read as "do nothing".

04 · What broke

4 · What the pipeline proved, and what broke on the way

Ordered by how much each one moved the numbers. Every item has either a fix that is in the tree or an open decision in §7.

harness · fixed

The CLI's session context leaks into the simulation: the date and the account email

Two independent findings from two domains' ledgers turned out to have one cause. The Claude CLI gives every session the real date and the account's email as context. Airline's policy says "The current time is 2024-05-15"; Haiku believed 2026-09-15 and refused to change "flown" flights (7 of 8 v0 failures). Retail's Haiku opened 20 of 20 conversations by looking the customer up under the author's address — a wasted turn every time, and a real address in every trace, 49 files across 5 runs, committed and pushed at M2.

Fix in tree: llm.redact() replaces the account email in every provider reply before it reaches tau2, and redact_tree() scrubs each run folder and optimiser output on write; all existing files are scrubbed (49 + 3). The date cannot be removed from the CLI's context; the airline prompt work in v1/v2 is the mitigation, and a system-level line in every v0 is the candidate in §7 (N-1). Open: the pushed history still carries the address; rewriting a public branch is your call (§7, N-6).

harness · fixed

79% fewer input tokens per call, same answers, retail 2 → 14

The inherited harness carried every connector tool the claude.ai account has into every SDK session — 47k input tokens per agent call on airline, 56k on retail — plus one Haiku call per session to name it. Ported DABStep-loop s02: strict_mcp_config=True and CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1. Measured on airline task 0: agent input 20,987 → 4,313 per call, user-sim conversation input 84,040 → 1,556, 70 s → 25 s, same reward. Retail v0 went from 2/20 to 14/20 — the old harness produced 21 tool calls in 110 turns; the lean one 145 in 265. run.json.harness = "lean" records it.

subscription · fixed

The 5-hour window ran out twice mid-batch; the adapter now waits for it

The first time, 22 conversations died with "session limit · resets 4:40pm" and two runs had to be deleted and re-run. seconds_until_reset() parses that message and run_query sleeps until the reset (cap 6 h) then retries, so a run pauses instead of failing. Nine waits are in the logs, 193–219 min each; the telecom test run spent about 3 h 15 min of its 12 h wall clock waiting. Cost of the design: wall-clock estimates in s00 §9 were off by the waits, not by the work.

adapter · fixed

Three CLI behaviours the provider had to absorb

  • "Reached maximum number of turns (1)" ended 7 of 20 airline conversations even though the reply had text: the provider now accepts any reply with text beside an error note, with max_turns=4 headroom.
  • The NL judge does json.loads on the reply; Haiku fenced it in ```json in 5 retail conversations: fences are stripped for tool-less replies.
  • Empty NL-assertion lists scored 0 in the gate replay; tau2 scores them 1.0. Banking's replay needed the real env kwargs (_build_env_kwargs) to rebuild the BM25 index. Gate is 80/80 after both.

loop · proved

The guard rails held on every cycle

Four optimiser sessions, 11–21 turns, 2.7–4.4 minutes each. None touched a file outside its version folder, none tried to run the benchmark, all four wrote a parseable diagnosis.json whose expected_to_fix could be checked against the gate's fixed list: airline c1 expected 8, fixed 4; retail expected 6, fixed 3; telecom expected 4, fixed 5. Optimiser input: 0.54–1.25 M tokens per session, almost all the condensed traces.

judge · observed

The retail judge decides one task in twenty

Retail's NL judge is the same Haiku on the subscription. Of the 10 retail failures across v0 and v1, 8 also fail a DB or action check — the judge is not what sinks them. Task 105 is the exception both times: DB correct, actions 1/1, NL assertion 0/1 ("agent should offer another payment method on file"); the judge's verdict is the whole reward there. That is the s00 §3 concern at its actual size: one task, and a plausible verdict on reading the trace. tau2loop gate reuses the recorded verdict rather than re-judging, so the number is reproducible but not re-checked.
