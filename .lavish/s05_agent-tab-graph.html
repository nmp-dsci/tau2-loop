Pick a run and a conversation, and every node of the agent shows what went in and what came out

Today's Agent tab draws how a model call reaches the subscription, then prints the version files. It never shows the agent doing anything. This rebuild copies DataAgentBench's Agent tab: a filter bar, the agent as a graph beside a node panel, and a replay underneath. It is reshaped for τ², where the agent is one of three parties and the grade comes from five checks. Every tool node carries a playground: re-run any call, with your own arguments, against the database as it stood at that message.

4 · Build — three API routes and one page rewrite

The graph and panels need nothing new on disk; the API just drops some of it today. The playground needs one new route, which rebuilds τ²'s environment in memory.

  1. The trial route keeps what trace_events() throws away

    GET /api/runs/{id}/{task}/{trial} returns each message's id, turn_idx, usage, generation_time_seconds and requestor, so a tool result pairs with its call. It adds task (scenario plus evaluation criteria, from data/tasks/<domain>.json) and the full reward_info. The domain's tool list gains type from τ²'s own Toolkit.tool_type(): read, write, generic or think.

  2. A run serves the agent it ran with

    GET /api/runs/{id}/agent returns the snapshot in runs/<id>/agent/, the hooks it defines, and the composed system prompt: system.md with the trace's policy in the slot, plus extra_context() run on that policy. The hook is deterministic and no model is called. Reading the run's snapshot rather than agents/ keeps the rule that the run folder is the record.

  3. The playground route runs one call in a rebuilt environment

    POST /api/runs/{id}/{task}/{trial}/tool with {name, arguments, at}. It builds the run's environment the way eval/rescore.py already does (the same constructor and, for banking, the same bm25 retrieval), then calls τ²'s Environment.set_state with the task's initial state and messages[:at]. That replays every write before message at, with strict=False as rescore uses. It then runs the one call through get_response. It returns the result, the error flag, whether the database hash changed, and a field-level diff of the records that changed. The environment is discarded after each call. Nothing reaches a model or the disk, so the route stays on in the demo image, bounded to the domain's own tool names, 8 KB of arguments and one call per request. The env-building code moves out of rescore.py into a shared eval/replay.py, so the grade and the playground cannot drift apart.

  4. lib/agentgraph.tsx: graph, panel, playground and replay

    A hand-laid SVG following the .dia contract, whose rows come from data: the domain's tools, split by type, and the task's reward basis. pages/Agent.tsx becomes the filter bar plus these three. The lens is ?run=&trial=&node=&step=. sessionStorage restores the last view, as DataAgentBench's AGENT_VIEW does. Old ?node= keys (provider, sdk, factory…) redirect to their new node, so bookmarks still land.

  5. Tests pin the addresses and the pairing

    routes.test.tsx drives /agent/airline/v2?run=20260915T132148Z_airline_v2_train&trial=airline/22/t1&node=tool:update_reservation_flights. test_api.py asserts that every committed tool result pairs with exactly one call. test_playground.py re-runs every recorded call in a committed run and requires its recorded result back; this page's precompute passes that on both runs (). It also covers the route refusing an unknown tool, oversize arguments and an at past the end, and it checks that the database file's hash is unchanged after a write.

5 · Risks — the playground is only as good as the replay

  • The user simulator makes tool calls in telecom. The committed telecom v1 train run has 126 user-side tool-call messages; the simulated customer toggles airplane mode and similar settings on their own phone. The graph needs a second tool group on the user's side, drawn only when a trace has requestor: user calls. Airline has none, so the prototype cannot show it.
  • Banking's tools belong to the task. 33 of banking_knowledge's 40 tasks carry user_tools. The user-side group is built per task, not per domain.
  • Traces run to 140 messages (the longest committed). The replay renders past row 60 on demand, and each panel output is capped with a "full text" toggle. The prototype caps tool results at 1,600 characters.
  • The graph's height depends on the domain, which has 13 to 16 tools. Rows come from the tool list, so the panel sits sticky beside a taller figure on retail.
  • The playground trusts the replay, so the replay is tested. Rebuilding state means re-running every earlier write. In these two runs, . A version of τ² whose tool code drifts would break that, and test_playground.py is the tripwire.
  • Tools do not enforce the policy; the agent does. The playground shows what τ²'s code accepts, not what the policy allows. On task 22, update_reservation_flights accepts the cabin change the agent refused, and it would equally accept one the policy forbids. The panel says so beside every result, so an accepted call does not read as "the agent was allowed to".
  • Banking must be rebuilt with the run's own retrieval. τ²'s dense-retrieval variants call an embedding API. The route must take the run's environment settings (bm25, as runner.py sets), never a default, or a playground call could bill a key the project does not hold.
  • A POST route in a read-only demo. It writes nothing and calls no model, but it is still compute on request. The bounds above (tool names, 8 KB, one call) keep it cheap. DEMO_MODE is not a reason to turn it off, since the demo's point is to be poked at.
  • τ²'s opening greeting has no usage. It is a fixed string, not a model call, so the agent node counts it as neither a step nor zero tokens.
