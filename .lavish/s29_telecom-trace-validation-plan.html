Our telecom traces already use the leaderboard's file format; what differs is what we record and how the conversations read

Eight text submissions on the tau2-bench leaderboard publish their telecom conversations. Those are the traces a fine-tuning set could reuse. I read two of them, Claude Opus 4.5 and GPT-5.2 (456 conversations each), against v2's 114. Both sides write tau2 1.0.1's results file, with the same policy and the same 114 tasks byte for byte. Three things differ. Our model layer drops three things the model produced. Our agent's turns are shaped differently: one call a turn and almost no markdown. Our customer is a different model. The plan builds a checker that scores the three layers against the leaders' range, then fixes what we record, then plays a 6-task example on a fork set up like the leaders' scaffold to show how close that gets.

01 · The goal — a conversation from either side becomes the same kind of training row

layer 1 · fileThe same results file, field for field

tau2's results JSON: the run's info, the tasks, and each simulation with its messages, its reward and its timing. A reader written for one side reads the other.

layer 2 · recordEach turn holds everything the model produced

The text, the calls with their real ids, and the reasoning where the provider returns it. The prompts each side was given must be recoverable too, or a training row cannot be rebuilt.

layer 3 · conversationThe turns read like the leaders'

Calls per turn, text beside calls, markdown, length and endings, all within the range the leaders span. The leaders differ from each other, so the target is their range, not one of them.

Layers 1 and 2 are about the record, and code can make them exact without changing what any model sees. Layer 3 is about behaviour: it moves only if the agent's setup moves, and it can only be measured.

What no trace can show

The leaders' agents got the history as native chat turns: the model's own tool calls and their results as tool blocks. Ours gets a system prompt and the history as text blocks, one a turn, its past calls written out as JSON (prompting.render_turn), even in native mode. Two traces can match message for message while their models were given different prompts. R4 records ours so a training row can say which it was.

The two clearest gaps are one call a turn and no markdown. Both may come from our setup more than from Haiku 5.5: the JSON contract puts every reply inside a JSON string, and both our asks say "plain text". The 6-task example in M5 is how to find out.

The customer is a different model on each side: gpt-5.2 at low effort for the leaders, Haiku 5.5 at high for us. This project bills only the Claude subscription, so gpt-5.2 cannot be our customer. Customer measures are reported and kept out of the score. The band widens once all 7 tau2 1.0.1 leaders are read (M3).

These are first-look numbers from 2 leaders, counted by hand. M2 makes the checker that counts them; M3 reruns them against all 7 tau2 1.0.1 leaders. The band is the leaders' min to max, widened by 5 points for rates and 10% for counts, and the checker prints each band so you can see what moved a measure in or out.

07 · The plan — seven milestones; only M5 calls a model

  1. M1

    Collect the leaders' telecom traces

    tau2loop leaderboard-fetch --domain telecom reads the board's manifest.json and submission.json files, downloads each text submission's telecom file (D1) to data/external/leaderboard/telecom/ (D4) and writes a committed manifest.json: submission, model, URL, bytes, sha256, tau2 version, customer and pass count. A file whose sha256 changes is refused.

  2. M2

    Build the checker

    tau2loop trace-check --domain telecom --run <id> … (src/tau2_loop/traces/check.py) reads tau2 results files and writes trace_check.json: F1–F9, R1–R4, C1–C8 with each value, band and result, and the customer measures apart. It is deterministic and calls no model. Tests run it on small fixtures cut from real files, one conversation from each side, and assert the scores.

  3. M3

    Baseline: v2 against the leaders, and each leader against the others

    Score v2's train and test runs. Then score each leader against the other six, which gives the ceiling: two standard-scaffold runs are not identical either. The baseline replaces the first-look numbers in §06.

  4. M4

    Record what the model gives us: R1–R4, for every version

    • R1: the text written beside a call goes into raw_data.choices[0].message.content, as litellm records it. Message.content stays as it is, so tau2, the customer and the agent's later prompts are unchanged.
    • R2: in native mode, a call keeps the SDK's toolu_… id. JSON mode has no provider id and keeps ours.
    • R3: a ThinkingBlock becomes reasoning_content and thinking_blocks in raw_data. It is never sent back to the model.
    • R4: each run folder gets prompts/: the agent's composed system prompt, the customer's additions and the tool schemas offered, with their sha256 in run.json.

    Record-only, so runner.SIM_RULES stays tau2_loop/2 and no run is replayed. Tests reproduce each loss before the fix. Runs already written stay as they are: they are immutable.

  5. M5

    The example: a fork set up like the leaders' scaffold, on 6 train tasks

    v3 = v2 with tool_mode: native, parallel_calls: true and a new call_text: true, which keeps the text beside a call in Message.content as tau2's own agent does (D2). It plays 6 train tasks, 2 a symptom, with the Haiku 5.5 customer at high, then the checker scores it against v2 and the leaders. Fig 4 is redrawn with v3's turn. v3 probes trace shape: it is not a challenger and is not promoted.

    make fork DOMAIN=telecom FROM=v2 TOOL_MODE=native PARALLEL_CALLS=true CALL_TEXT=true WHY="s29: trace shape like the standard scaffold"
uv run tau2loop eval --domain telecom --agent v3 --split train --task '<id 1>' … --task '<id 6>' --note "s29 example"
uv run tau2loop trace-check --domain telecom --run <v3 run> --run 20261016T124631Z_telecom_v2_train
  6. M6

    Export both sides to one training format and check the rows match

    tau2loop export-sft writes one JSONL row per passed conversation, from a leader's file or ours: messages in the OpenAI chat fine-tuning shape (assistant tool_calls with JSON-string arguments, tool turns with tool_call_id), the native tools schemas and a source block (submission or run, model, scaffold, customer). The system message is tau2's stock agent prompt plus the policy (D5). Train ids only (D3). The checker then runs on the rows: both sides must validate against one JSON schema, with the same keys on every row.

  7. M7

    A results page

    .lavish/s30_…: the three scores before and after M4, v3's example beside v2 and the leaders, the ceiling, and what stays different and why. Each milestone is its own commit; pushing and the PR wait for your say.

Cost: M1 downloads 413 MB (D1 = A). M5 plays 6 conversations, about 2M agent input tokens at v2's rate of 365K a conversation, roughly 20–30 minutes. Nothing else calls a model.
