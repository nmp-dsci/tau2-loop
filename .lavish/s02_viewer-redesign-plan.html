Nine tabs become six, with one drill-down: Experiment → task → trace

Your review of the app came back with nine points; they resolve into four decisions. The home page should answer "how good is the champion, per domain, against the board". Data and Tasks are one thing. Runs, Loop, Trace and Run are one drill-down. Gate and Evolution are one lineage view — a champion trunk with challenger branches, merged or closed, read straight from the ledger. Architecture becomes a walk-through you can step with a real trace. And three of the "null" complaints are bugs, not design: a stale server, test runs polluting MLflow, and cycle rows that never join their eval metrics.

04 · Architecture

4 · Architecture — the same diagram, driven by a real trace

Pick an experiment and a task; the trace's messages become steps. Each step lights the box it belongs to (user-sim → orchestrator → our factory → SDK → tool → evaluator) and the right-hand panel shows exactly what crossed that edge: the system prompt as assembled from agents/<domain>/vN/system.md + policy + extra_context, the JSON reply contract, the parsed tool call, the tool result, the user-sim's reply, the evaluator's verdict per component. The system prompt you could not see is step 1. Data source: runs/<run>/traces/<task>.json, which already holds every message and tool call — no new capture needed, one new API route to render the prompt for a version.

07 · Gate

7 · Gate — a trunk of champions, branches of challengers, read from the ledger

No picker. For each domain, registry.json gives the trunk (every promotion, in order) and ledger.jsonl gives one branch per cycle: it merges when promoted, closes amber when held, closes red when rejected. Each node carries fixed / broke, p, rule and the run id. Click a branch and Evolution's four panels open under the graph for that cycle — the diagnoses, the prompt diff, the change log, the optimiser's closing note. The page re-reads the files on every load, so a cycle that finishes shows up on refresh, and the demo image serves the committed state.

08 · Under the hood

8 · The three bugs behind "null", and the data the new tabs need

bug · fixed now

Stale server

The :8081 process predated the harness field in run.json; RunMeta(**json) raised on the newer runs and /api/runs?domain=… returned 500 — so Gate's pickers and half of Runs were empty. Restarted on current code; the demo image never has this problem because it is built from the commit it serves. Prevent: make viewer restarts the server, and /healthz reports code_sha so the footer shows when the server is behind the checkout.

bug · to fix first

Test suite writes to the live MLflow store

tests/test_loop.py runs a fake cycle that calls the real mlflow_log; every make test added an airline-cycle-1 · promote row with zero tokens. Seven are there now, plus eval rows for four runs that were deleted and re-run. Fix: tests set MLFLOW_TRACKING_URI to a temp dir via a conftest fixture; delete the seven rows and the orphaned eval rows; make snapshot re-exports.

bug · to fix first

Cycle rows never join their eval metrics

A cycle's MLflow run carries only optimiser tokens by design; the pass rate and eval tokens are on the challenger's eval run. The Runs page printed the cycle row's own metrics, hence null. Fix: the Experiments table is built from ledger.jsonl + runs/ directly (MLflow stays the index, not the source), and a cycle row shows its challenger run's summary plus the verdict.

09 · Build

9 · Build order — bugs, then the two tabs that carry the most, then the rest

All frontend, no model calls, nothing from the subscription window. Each step ends with the app reviewable on :8081 and a commit.

V0½ h

Bugs first

Test fixture isolating MLflow; delete the seven fake cycles and orphaned eval rows; snapshot; make viewer restarts; footer shows server-vs-checkout sha. Experiments API built from files.

V12 h

Result + Experiments

Home page with overall, per-domain, board comparison from the snapshot; Experiments table with per-question mean/p95 and the three-level drill-down (Run and Trace pages move under it). Nav drops to six.

V21.5 h

Gate lineage

SVG lineage per domain from registry + ledger; click → Evolution's panels; Evolution and Compare pages removed.

V31.5 h

Data with tasks

Domain selector, intro band, stat cards, full task table with filters and expansion; Tasks page removed; "run ›" links into Experiments.

V42 h

Architecture walk-through

Run/task picker, step model over the trace, lit diagram, side panel including the assembled system prompt; Agents gets the ask-vs-design table.

V5½ h

Demo image + deploy

Rebuild the keyless image with the new app; smoke; then M5 when the SSO login is done.

risks

  • Trace files are 100–400 KB each; the drill-down loads one at a time and the Data tab's task table is paginated at 40 rows, so the demo image on App Runner stays fast.
  • The leaderboard snapshot goes stale; the Result page prints its date beside every board number, and refresh is a deliberate CLI command, never a page-load fetch.
  • The lineage graph is hand-laid SVG (one branch per cycle); at ~10 cycles per domain it needs a scrolling lane — fine for this project's scale.

not in this plan

  • Any new runs — the numbers on the new pages are the ones on s01. Re-gating airline v2 and the banking cycle are s01 N-2/N-3 and cost window.
  • Live MLflow embedding — MLflow stays a link.
  • Editing agents from the app — it stays read-only; the loop is the only writer.
