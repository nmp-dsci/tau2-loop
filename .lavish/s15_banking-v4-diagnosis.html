Diagnosis · banking_knowledge · v4's 31 train failures of 60

v4 has the evidence and acts before using it: 24 of 31 failures

I ran the loop's diagnosis step on v4's 31 train failures, with the next cycle's prompt, fence and model, writing to a scratch folder so no v5 exists. I asked one more question of every failure: did the agent act on a guess, and was the evidence it needed retrieved? Then I set the answers beside the leaders' traces, the published work on getting a model to think before it acts, and a replay of candidate guardrails.

The short version

  • Guessing, with the evidence in hand. The optimiser judged 24 of 31 failures acted on a guess. In 24 the document or record that settled the step was already in the conversation, unused. It was never retrieved in 5, and retrieved only after acting in 2.
  • Less research before the first write. v4 makes 9.0 look-ups before its first write, against 16.8 (Opus 5) and 13.4 (Qwen 3.8 Max). It has read 66% of the required documents by then; they have 78% and 69%.
  • Thinking longer alone is not the gap. Qwen spends fewer output tokens before its first write (6,304) than v4 (7,341) and passes more. Opus spends twice as many. What separates them is reading the procedure and checking the record before writing.
  • 12 failures are tasks the leaders usually pass (5–8 of 8). On 11 of those 12, v4 looked up less before its first write than the leaders' mean. 13 failures are tasks the leaders also fail (0–1 of 8).
  • Generic gates are noise; targeted ones work. A replay shows a “leads not followed” gate firing on 29% of failed and 41% of passed conversations. The useful guardrails check a named procedure (a close needs the transactions read).
  • Proposal for v5: a five-point pre-write rubric and a steering line in the prompt (P1), the targeted guardrails (P3), the KB's dispute-amount rule (P4), and your choice of effort or model (Q1). I'd defer the fitted dispute checks and every generic gate.

Most read-but-not-applied rules can become checks the agent cannot skip

your question · task_008 · could this be a guardrail or an asset the agent checks?

Yes. Doc _042 is a table: every reason code has a tier, and the rule is “always the highest tier that applies”. That table can live in checks.py as data, and a check can send a transfer back once when a lower-tier code is chosen while a Tier-1 signal holds. In task_008 the customer pressed for offers the agent had said were unavailable (Tier 1, customer_demands_after_unavailable_offer_refusal); v4 chose the Tier-2 unconfirmed_external_communication. One gap first: today no hook sees a transfer. check_write runs only on tools tau2 marks as writes, and transfer_to_human_agents is not one. Letting the check see transfers is a small harness change, and two of the conversions below need it.

There are two kinds of deterministic check. One computes the answer, so the model cannot get it wrong: the call is blocked until the procedure's read has run. The other is triggered by code every time but leaves the decision to the model, which must look again with the rule in front of it. Mine the guardrails from the 44 procedure documents, not from the test questions

your question · could guardrails be learned from the documents or the questions, run on all train and test questions?

From the documents, yes: they are the right source. The knowledge base is shared by train and test, and its procedures are written per tool and per product, not per customer. Rules mined from it therefore cover test's question types without reading a test question. It is small: of 698 documents, 44 name a tool and 150 read as procedures. Between them they cover 35 write and transfer tools, in about 91,000 characters for the 34 that are both.

From the test questions, no. Banking promotes on test: v4 became champion because it passed 14 test tasks to v3's 6. Rules learned from test questions would make that comparison meaningless, because the agent would have been fitted to the exam. It would also break the project's rule that no optimiser sees a test task (CLAUDE.md), and our scores would no longer compare with the leaderboard's, which never saw the tasks. Train questions are allowed, but they add little beyond the documents and invite rules fitted to graded answers, like the optimiser's 30-day liability window.

  1. Mine. One read-only session (Opus, on the subscription) reads the 150 procedure documents and writes each rule as a record: the write or transfer tool it governs, its kind, its parameters, the document id and the sentence it comes from. It needs no labels, which is the unsupervised part.
  2. Compile. One generic rule engine in checks.py and memory.py reads the records as data. A new procedure is then a new record, not new code. Kinds that code can check become checks; the rest become one prompt line per tool.
  3. Validate on train only. Replay every rule over v4's 60 train conversations and the leaders' 240 train trajectories, with no model call. Drop any rule that fires on a passed conversation, because it would block correct behaviour; keep those that fire only on failures. This uses train's labels, so strictly it is semi-supervised.
  4. Gate on test, unseen. The usual challenge then measures whether rules mined from documents generalise to customers the miner never saw.
