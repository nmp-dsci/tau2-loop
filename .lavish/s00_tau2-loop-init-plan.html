A policy agent on τ²-bench, with a scored self-improving loop

Discovery is done: the benchmark ships every task and every answer key, so honesty comes from a random 20 / 20 split we cut and commit ourselves, per domain, and a pass^k number with its denominator. The build reuses DABStep-loop's loop wholesale and changes only what τ²-bench forces: the harness runs the tools, so the agent under test is a registry factory with two editable surfaces — and every model call, ours and tau2's, is routed through the Claude subscription.

01 · Goal

1 · Goal — one command scores a versioned agent per domain, then the loop takes over

Same shape as DABStep-loop: make eval DOMAIN=airline writes an immutable run folder with a pass rate, make loop DOMAIN=airline runs one optimiser session that may edit two files, and a statistical gate decides promotion. What this build proves is the loop on our own 20-task train split, in each of the four scored domains; a leaderboard run (all tasks × 4 trials) comes after and is a separate decision.

02 · Discovery

2 · Discovery — nothing is held out, so the "test" split is ours to keep honest

Every domain ships its tasks with evaluation_criteria (reference actions, NL assertions, env assertions) in the repo. train and test exist for RL work and partition the public base set exactly; the README asks for base on the leaderboard. The board is a PR of your own trajectories to taubench.com, validated by tau2 submit prepare | validate | verify-trajs — self-reported, not graded on a hidden set.

Train / test

Yes, but both are public — so we cut our own

tau2's train / test partition the public set (airline 30 / 20, retail 74 / 40, telecom 74 / 40; banking has none). We ignore them and draw a random 20 / 20 per domain from base; the remainder is an untouched reserve. Test is opened only after a promotion.

Holdout submission

No — a PR of your own runs

Leaderboard needs all tasks in a domain, ≥4 trials, same agent and user LLM across domains, base split; any scaffold change is submission_type: custom. A Claude user simulator instead of the recommended gpt-5.2 makes ours custom regardless.

Enough data?

20 train tasks × 4 domains = 80 conversations per full cycle

DABStep-loop ran on 10 gold tasks. A Haiku agent at roughly 60–70% on airline and retail leaves 6–8 failures per domain per cycle, and banking (board top 55.2%) will fail more than half — enough for a diagnosis every cycle.

03 · Scoring

3 · Scoring — reward is a product of checks, and only retail needs a judge

evaluate_simulation() multiplies the components named in each task's reward_basis; any 0 zeroes the task, and a run that ends for a reason other than agent- or user-stop scores 0 before any check. Success is binary (reward within 1e-6 of 1.0), so pass^k is the only headline number: pass^k = C(successes, k) / C(trials, k) averaged over tasks (src/tau2/metrics/agent_metrics.py:113).

  • Where does LLM-as-judge belong in our loop, then? Not in the score. The judge already inside tau2 is evaluator_nl_assertions.py (retail only); --auto-review adds a diagnostic Opus reviewer. Our own Sonnet reads failed traces to write a diagnosis, exactly as DABStep-loop's reflector does — it explains failures, it never grades them.
  • Is there a free partial signal? Yes. partial_action_reward (matched reference actions m/n, split READ / WRITE) and per-check action_checks[] are computed on every run regardless of basis. They go into the ledger and the optimiser prompt as evidence, never into the gate.
  • Can we re-score without re-simulating? tau2 evaluate-trajs <paths> re-grades saved trajectories, which is how we re-check a retail judge decision without paying for the user simulator again.

04 · Data shape

4 · Data shape — the policy fits in the prompt everywhere except banking

Airline's policy.md is 1,313 words (about 1.7k tokens); retail 1,158; telecom main + manual about 3.7k words. None of that needs retrieval. The environment owns the database and the tools; the agent only ever sees tool schemas and tool results. Only banking_knowledge (698 documents, policy built per task by build_policy()) is a genuine RAG problem, and tau2 already ships --retrieval-config bm25 | openai_embeddings | full_kb … for it.

Decisions this shape forces

  • Tools — supplied by the harness, not by us. Airline exposes 15 @is_tool functions from src/tau2/domains/airline/tools.py; the orchestrator executes them. Our agent emits tool calls, it does not run them. The optimiser therefore cannot add a tool; it can add pre-call checks and state tracking in helper.py.
  • RAG — not for airline or retail. Stuff the policy. Restructuring the policy (ordering rules, adding a refusal checklist) is the main lever system.md has, and it is exactly what the top custom submissions did.
  • Banking runs with local BM25 retrieval. Board top is 55.2% pass^1, so it is where a scaffold change is most visible. It needs the knowledge extra and a retrieval config; bm25 (rank-bm25, no API) is the only one that runs on a subscription, so it is the frozen default in agent.yaml. Its 20 / 20 split is cut from all 97 tasks.

05 · Domains

5 · Domains — all four scored domains, a random 20 / 20 split each, cut once and committed

Decided in review: the loop runs on every scored domain, not airline alone. Each domain gets its own split drawn at random from the public base set with a fixed seed, written to data/splits/<domain>.json by make splits, and never regenerated — the file is the record, the seed is only how it was made. Mock (10 tasks) is the keyless smoke test and is never scored.

  • Why our own split rather than tau2's? tau2's train / test are fixed lists chosen for RL work, and banking has none. A random draw with a committed seed is reproducible, uniform across domains, and the CI gate can re-derive the file and fail if it was edited by hand.
  • Why 20 test and not the rest? Test is run after every promotion. Keeping it to 20 keeps a promotion cheap on a subscription quota; the reserve remains available for a final all-tasks run.
  • One loop or four? Four ledgers, one per domain (loop/<domain>/ledger.jsonl), because the policy and therefore system.md differ per domain. helper.py may share code through a common module, but each domain's version folder is fingerprinted on its own.

06 · Architecture

6 · Architecture — tau2 runs the environment; our agent is a registry factory with two surfaces

tau2's orchestrator drives a half-duplex turn loop between the user simulator, our agent and the domain environment. Our package wraps it: a factory registered in tau2.registry loads agents/<domain>/vN/system.md and helper.py, calls the model under test, and returns an AssistantMessage with tool calls. Everything DABStep-loop owns — versions, runs, ledger, gate, MLflow, viewer — is copied and rewired to tau2.runner.batch.run_tasks(). One thing is new: a subscription adapter that stands in for tau2's LiteLLM calls.

07 · Agent v0

7 · Agent v0 — Haiku 4.5 in every role, on the subscription, the policy verbatim, no helper

Decided in review: there are no API keys, so every model call runs through the Claude Agent SDK on the subscription, and the default model in every role is claude-haiku-4-5. v0 is an honest baseline: tau2's own AGENT_INSTRUCTION plus the unmodified policy.md as system.md, an empty helper.py, and agent.yaml freezing model, temperature 0, max steps 200 and (banking) retrieval: bm25.

  • Is a Haiku user simulator good enough? Unknown until M2. The user simulator sets the difficulty: a weak one forgets its own instructions and can make tasks easier or noisier. The ledger header records it, so a later switch to Sonnet is a new ledger with its own baseline, not a silent change. Raise it in §13 if you want Sonnet from the start.
  • Does a Claude judge change retail's score? Yes, relative to the board (gpt-4.1 judge). Our numbers are internally consistent — same judge for champion and challenger — but a retail leaderboard row would be custom with the judge named in the methodology notes.
  • What does the subscription cost us? Quota, not dollars: a per-window message budget shared with your own Claude Code use. §9 is now in conversations and SDK turns, and the loop's concurrency is capped so a cycle does not exhaust a window.

08 · The loop

8 · The loop — DABStep-loop's mechanics, gated on train, reported on test

One cycle is one optimiser session. It reads the ledger first (what was tried, per task), the champion's surfaces, and one evidence block per failing train task in that domain: the user scenario, the policy clauses cited in description.relevant_policies, the reference actions vs the actions taken, the DB diff, and a condensed trace. It must write diagnosis.json and change both surfaces. The harness runs the challenger on the same 20 train tasks and promotes only on a McNemar win. Each domain has its own ledger and champion; make loop DOMAIN=retail runs one cycle there.

  • What can the optimiser change in a tool-owned environment? system.md: policy restructuring, a pre-write confirmation rule, a refusal checklist, a state summary format. helper.py: functions the factory calls around the model — validate a tool call's arguments against what the user has actually confirmed, track booked / cancelled state, block a write until the required reads have happened. No new tools, no model change.
  • Why not unsupervised, like DABStep's cycle 6? Not needed: every tau2 task has a key. The unsupervised extension (families, probes, invariants) stays out of this build; it becomes relevant only if we optimise on the 2,285-task telecom set.
  • Trials during the loop. One trial per cycle keeps a cycle to 20 conversations and the McNemar table clean. pass^4 is computed only on 4-trial runs, so it never appears without its denominator.

09 · Budget

9 · Budget — quota, not dollars: a train cycle is 20 conversations, a full sweep 80

On the subscription the cost is a share of a rolling message window, spent by the agent, the user simulator, the judge (retail) and the optimiser. tau2 publishes no turn counts; the board's cost fields imply roughly 10–20 model calls per airline conversation.
