A policy agent on τ²-bench, with a scored self-improving loop

Discovery is done: the benchmark ships every task and every answer key, so honesty comes from a split we keep ourselves and a pass^k number with its denominator. The build reuses DABStep-loop's loop wholesale and changes only what τ²-bench forces: the harness runs the tools, so the agent under test is a registry factory with two editable surfaces.

02 · Discovery

2 · Discovery — nothing is held out, so the "test" split is ours to keep honest

Every domain ships its tasks with evaluation_criteria (reference actions, NL assertions, env assertions) in the repo. train and test exist for RL work and partition the public base set exactly; the README asks for base on the leaderboard. The board is a PR of your own trajectories to taubench.com, validated by tau2 submit prepare | validate | verify-trajs — self-reported, not graded on a hidden set.

Train / test

Yes, but both are public

train ∩ test = ∅ and train ∪ test = base in airline, retail and telecom. We optimise on train, report test only after a promotion, and never open a test trace during a loop cycle.

Holdout submission

No — a PR of your own runs

Leaderboard needs all tasks in a domain, ≥4 trials, same agent and user LLM across domains, base split; any scaffold change is submission_type: custom. Recommended user sim is gpt-5.2.

Enough data?

30 train tasks × 4 trials = 120 signals

DABStep-loop ran on 10 gold tasks. With a Haiku-class agent at roughly 60–70% on airline, expect 9–12 failing tasks per cycle — enough for a diagnosis each cycle, and retail's 74 adds a second domain later.

03 · Scoring

3 · Scoring — reward is a product of checks, and only retail needs a judge

evaluate_simulation() multiplies the components named in each task's reward_basis; any 0 zeroes the task, and a run that ends for a reason other than agent- or user-stop scores 0 before any check. Success is binary (reward within 1e-6 of 1.0), so pass^k is the only headline number: pass^k = C(successes, k) / C(trials, k) averaged over tasks (src/tau2/metrics/agent_metrics.py:113).

  • Where does LLM-as-judge belong in our loop, then? Not in the score. The judge already inside tau2 is evaluator_nl_assertions.py (retail only); --auto-review adds a diagnostic Opus reviewer. Our own Sonnet reads failed traces to write a diagnosis, exactly as DABStep-loop's reflector does — it explains failures, it never grades them.
  • Is there a free partial signal? Yes. partial_action_reward (matched reference actions m/n, split READ / WRITE) and per-check action_checks[] are computed on every run regardless of basis. They go into the ledger and the optimiser prompt as evidence, never into the gate.
  • Can we re-score without re-simulating? tau2 evaluate-trajs <paths> re-grades saved trajectories, which is how we re-check a retail judge decision without paying for the user simulator again.

04 · Data shape

4 · Data shape — the policy fits in the prompt everywhere except banking

Airline's policy.md is 1,313 words (about 1.7k tokens); retail 1,158; telecom main + manual about 3.7k words. None of that needs retrieval. The environment owns the database and the tools; the agent only ever sees tool schemas and tool results. Only banking_knowledge (698 documents, policy built per task by build_policy()) is a genuine RAG problem, and tau2 already ships --retrieval-config bm25 | openai_embeddings | full_kb … for it.

Decisions this shape forces

  • Tools — supplied by the harness, not by us. Airline exposes 15 @is_tool functions from src/tau2/domains/airline/tools.py; the orchestrator executes them. Our agent emits tool calls, it does not run them. The optimiser therefore cannot add a tool; it can add pre-call checks and state tracking in helper.py.
  • RAG — not for airline or retail. Stuff the policy. Restructuring the policy (ordering rules, adding a refusal checklist) is the main lever system.md has, and it is exactly what the top custom submissions did.
  • Banking is the stretch, not the start. Board top is 55.2% pass^1, so it is where a custom retrieval scaffold would be visible — but it needs the knowledge extra, per-task policy building and a retrieval config, and it has no train / test split.

06 · Architecture

6 · Architecture — tau2 runs the environment; our agent is a registry factory with two surfaces

tau2's orchestrator drives a half-duplex turn loop between the user simulator, our agent and the domain environment. Our package wraps it: a factory registered in tau2.registry loads agents/vN/system.md and helper.py, calls the model under test, and returns an AssistantMessage with tool calls. Everything DABStep-loop owns — versions, runs, ledger, gate, MLflow, viewer — is copied and rewired to tau2.runner.batch.run_tasks().

08 · The loop

8 · The loop — DABStep-loop's mechanics, gated on train, reported on test

One cycle is one optimiser session. It reads the ledger first (what was tried, per task), the champion's surfaces, and one evidence block per failing train task: the user scenario, the policy clauses cited in description.relevant_policies, the reference actions vs the actions taken, the DB diff, and a condensed trace. It must write diagnosis.json and change both surfaces. The harness runs the challenger on the same 30 train tasks and promotes only on a McNemar win.

  • What can the optimiser change in a tool-owned environment? system.md: policy restructuring, a pre-write confirmation rule, a refusal checklist, a state summary format. helper.py: functions the factory calls around the model — validate a tool call's arguments against what the user has actually confirmed, track booked / cancelled state, block a write until the required reads have happened. No new tools, no model change.
  • Why not unsupervised, like DABStep's cycle 6? Not needed: every tau2 task has a key. The unsupervised extension (families, probes, invariants) stays out of this build; it becomes relevant only if we optimise on the 2,285-task telecom set.
  • Trials during the loop. One trial per cycle keeps a cycle under $5 and the McNemar table clean. pass^4 is computed only on the 4-trial runs in §11, so it never appears without its 200-conversation denominator.

10 · Repo

DABStep-loop's .gitignore, .env.example, pre-commit (gitleaks + ruff) and the billing guard in llm.py come across unchanged. tau2-bench is a pinned git dependency, never vendored — its 816 MB stays out of our history.
