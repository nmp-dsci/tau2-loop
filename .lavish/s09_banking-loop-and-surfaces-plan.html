3 · Train and test errors — reading test failures spends the only holdout

The short answer: yes, the optimiser can read both, but then no honest number is left. Once it has read the test failures, the test score measures what it was fitted to. Banking has 0 of its 97 tasks in reserve to replace the test. The worry behind the question is real, though. Today the gate decides on the same train tasks the optimiser read, so the gate is grading the optimiser's own homework (s08 §4, where PRISM kept a separate gate set and DSPy warns that reusing train as validation makes GEPA overfit).

4 · Five surfaces — the diagnosis picks where a fix lives

Today the optimiser may write two files, and helper.py's hooks can neither see the conversation nor stop a call. on_tool_call silently rewrites a call's arguments, on_reply rewrites a message, and extra_context appends fixed text to the prompt once. So almost every lesson lands in system.md. On airline that file grew from 5,259 to 11,175 characters over the cycles, and no learned version has beaten the stock prompt on Sonnet 5 (s08 §4). The s08 research found the opposite pattern in the published agents: checks at write time and guidance every turn moved airline more than prompt text did.

All five run in our harness, agent/factory.py, around the model call. tau2 and the sealed agent container don't change. A check blocks a given call once, then lets the retry through; blocking every time is how ToolGuard lost 14 points. Memory resets with each conversation, because carrying facts between conversations would let a train conversation teach a test one during a run.src/tau2_loop/agent/factory.py · src/tau2_loop/agent/compose.py (HOOKS) · .lavish/s08_airline-agent-field-notes.html §2

Checks, memory and guidance are code rather than prompt. They cost no extra model call except a retry after a failed check, and each fits one kind of failure the diagnosis can name.

5 · The optimiser — diagnose, route, then write only the routed files

You asked for a diagnosis agent that chooses what to update, with everything packaged into the next version. I'd split today's single session in two. A diagnosis session reads the failures and, for each one, names one root cause and the surfaces that fit it. It writes only diagnosis.json. The harness then routes: only the named files may be written this cycle. A writer session makes the edits, and the harness packages the result into the next version.

Fig 6 · one cycle with a routing diagnosis

Dashed nodes are new. Splitting the session means a diagnosis can't talk itself into a fix it has already written. It also lets the harness refuse an edit no diagnosis asked for, and keeps the routing decision in the ledger apart from the diff. The cost is one extra Opus session a cycle.src/tau2_loop/loop/optimiser.py (run_optimiser, guard_writes) · src/tau2_loop/loop/run.py (run_cycle)

Guards on the package

  • Write guard. Only the routed files and diagnosis.json may be written. This extends today's PreToolUse hook and checksum.
  • No model and no network inside a hook. checks.py, memory.py and guidance.py may import only an allow-list of standard-library modules; an AST check refuses the version otherwise.
  • Leak guard. The harness refuses a version whose files contain any customer id, name, email or account number from the tasks' data. The test split has different customers; DataAgentBench's G2 guard did the same for gold values.
  • Budgets, proposed. Guidance at most 600 characters a turn. system.md at most 1,500 characters longer than its champion's.

6 · The experiment — two challengers from one champion

v2today's optimiser on v1's read-half failures: system.md and helper.py only v3the routing optimiser on the same failures, with all five surfaces open bothgated against v1 on the gate half, and run on test; 194 conversations, about 5 hours readsv2 against v3 on the same tasks answers this plan's question: does choosing the surface beat writing every fix into the prompt?

One trial on a 24-task gate can't separate a one- or two-task difference from noise: the same airline bytes flipped 5 of 25 tasks between two runs (s08 §3). A small gap is a direction, not a result, and would earn a second trial on the gate half before anything is built on it. Airline could take the routing optimiser next, as cycle 6 from v3, where a round-trip check would catch Opus's JFK → JFK bookings.

8 · Risks — over-blocking, tokens and attribution

  • Over-blocking. Hard blocks cost ToolGuard 14 points. Here a check blocks a call once, then lets it through.
  • Tokens. Per-turn guidance cost IRMA 50% more input. Banking already spent 251k agent input tokens a conversation on Haiku; guidance has a character budget.
  • Attribution. Five surfaces can change in one version. The ledger records which ones did. Re-running a held version's broken tasks with one surface reverted (s08 O3) comes later.
  • A check that encodes an answer. The leak guard refuses any customer data in the files, and the test split's customers differ.
  • Noise. One trial, and a 24-task gate under option B (§6).
  • Time. About 7.5 hours of runs to the experiment's verdict. The loop refuses a duplicate of a run in flight and re-runs one that died.
  • Not the board's number. BM25 (or BM25 with grep) against AllTools with OpenAI embeddings, and a Haiku user against GPT-5.2.
  • A rule change. The optimiser's reach grows from two files to five. Everything it may touch stays inside the version folder.
